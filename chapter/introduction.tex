\chapter{绪论}

\section{研究背景与研究意义}

在互联网的时代，数据库系统是信息基础设施的核心组件，几乎支撑了所有关键业务系统的运行\cite{sql-for-Ai}。
从在线交易、社交网络到云计算与人工智能应用，海量数据的高效存储、实时访问与可靠管理，直接决定了上层业务的性能、可用性与安全性\cite{Cattell2011, Stonebraker2010}。随着互联网业务规模的持续扩大，分布式和云原生架构快速普及，传统的集中式数据库在扩展性、可用性以及运维成本方面逐渐暴露出难以克服的瓶颈，
对于满足大规模在线服务与大数据业务的需求，显得十分乏力\cite{Agrawal2016}。
分布式数据库在这样的背景下，应运而生。
通过在多节点上对数据进行分片与复制，实现了水平扩展与高可用，已成为支撑大规模在线服务与大数据业务的关键技术路径\cite{Ozsu2011}。

事务（Transaction），是支持数据一致性和隔离性，支撑上层业务具体需求的核心机制\cite{Gray1993}。
在数据库系统中，事务是作为单个逻辑工作单元执行的一系列操作的集合。
事务的引入，是为了确保数据库在并发访问和系统故障的情况下，依然能够保持数据的完整性和一致性。
一个标准的数据库事务需要满足四个基本特性，通常被称为 ACID 特性\cite{acid,Haerder1983}：
\begin{itemize}
      \item \textbf{原子性（Atomicity）：\\}
            事务中的所有操作要么全部成功执行，要么全部不执行。
            如果事务执行过程中发生错误，系统必须回滚（Rollback）到事务开始之前的状态，
            确保不会出现"部分完成"的中间状态。
            原子性保证了事务的"不可分割性"。

      \item \textbf{一致性（Consistency）：\\}
            事务执行前后，数据库必须从一个一致性状态转换到另一个一致性状态。
            这意味着事务的执行不能破坏数据库的完整性约束（如主键约束、外键约束、业务规则等）。
            一致性是事务执行的最终目标，确保数据的语义正确性。

      \item \textbf{隔离性（Isolation）：\\}
            多个事务并发执行时，每个事务的执行不应受到其他事务的干扰。
            隔离性要求系统提供适当的并发控制机制，使得并发事务的执行结果与串行执行的结果等价。
            根据隔离程度的不同，数据库系统通常定义了多个隔离级别，如读未提交（Read Uncommitted）、
            读已提交（Read Committed）、可重复读（Repeatable Read）和可串行化（Serializable）等。

      \item \textbf{持久性（Durability）：\\}
            一旦事务提交（Commit），其对数据库的修改必须永久保存，即使系统发生故障（如断电、崩溃）也不会丢失。
            持久性通常通过日志（Log）机制和数据持久化技术来实现。
\end{itemize}

然而，在分布式环境下，传统的 ACID 特性面临着新的挑战。由于数据分布在多个物理节点上，网络延迟、节点故障和分区容错等问题使得实现严格的 ACID 特性变得极为复杂且代价高昂。
因此，分布式数据库系统往往需要在一致性（Consistency）、可用性（Availability）和分区容错性（Partition Tolerance）之间进行权衡\cite{Brewer2000, Gilbert2002}，
分区容错性是分布式系统的基础，故而在设计分布式数据库时，往往需要在一致性和可用性之间进行权衡。

对分布式场景下支持事务的数据库的研究，尤其是对于混合事务隔离级别，可以在运行时主动选择合适的隔离级别的算法设计，具有重要意义\cite{Terry2013, Bailis2014}。

混合隔离级别（Mixed Isolation Level，MIL）允许系统中的不同事务根据自身的业务需求，并发地运行在不同的隔离级别下。以MySQL为例，对一致性要求极高的转账业务可以使用可串行化（Serializable）隔离级别，而对性能敏感但对一致性容忍度较高的日志分析业务则可以使用读已提交（Read Committed）甚至读未提交（Read Uncommitted）隔离级别。这种灵活性使得数据库系统能够在保证关键业务数据正确性的同时，最大化系统的整体吞吐量和并发性能。

目前MySQL和PostgreSQL等主流数据库产品已经支持了混合隔离级别（MIL）的功能。MySQL 默认重复读，官方对混合使用持谨慎态度，警示不同级别下间隙锁差异可能引发死锁或主从一致性问题。PostgreSQL 默认读提交，官方态度更为开放，鼓励依业务场景灵活配置甚至使用可串行化，但强调应用层需处理序列化失败重试。综上，两者虽均允许混合配置，但 MySQL 侧重锁机制兼容性风险，PostgreSQL 侧重事务重试机制，测试时需针对性验证隔离级别交互带来的并发效应。

尽管MIL在业界被广泛采用，但不同数据库产品中MIL实现的语义是不明确且高度可变的，而且缺乏行业范围的共识或统一的正式规范。这种模糊性源于这样一个事实：现有的理论基础——例如基于冲突和视图可串行化的理论——在很大程度上假设所有事务都运行在相同的隔离级别下。在多版本并发控制（MVCC）环境中，不同版本可见性规则的事务之间复杂的交互（例如SER与RR或SI的交互）仍然是一个缺乏正式和全面理论描述的开放问题。这一缺陷导致程序员对其应用程序的正确性和可预测性产生相当大的顾虑，从而阻碍了MIL在关键生产环境中的更广泛采用。目前对于混合隔离级别的研究仍处于起步阶段，近期Bouajjani等人的工作\cite{bouajjani2025complexity}使用黑盒的方式测试数据库对隔离级别的保证，基于白盒的测试方法和形式化的隔离级别定义仍然是一个重要的研究方向。
因此，深入研究MIL的理论基础，建立严格的MIL操作语义模型，对于构建高可信、高性能的分布式数据库系统具有重要的科学意义和应用价值。


\section{研究现状与挑战}
\subsection{研究现状}
围绕分布式事务、隔离级别与形式化验证的研究，现有工作已经在事务理论、并发控制、多版本机制以及一致性建模等方面积累了较为扎实的基础\cite{Gray1993,berenson1995critique,Terry2013,Bailis2014,Schultz2015}。然而，就混合隔离级别场景而言，现有研究仍存在若干关键问题，尚不足以为分布式数据库系统提供统一、严谨且可落地的理论与方法支撑。

首先，现有研究对混合隔离级别的语义刻画仍不充分。传统隔离级别理论大多建立在“所有事务运行于同一隔离级别”的前提之上，其核心目标是描述单一隔离策略下允许或禁止的异常行为。然而，在混合隔离级别场景中，不同事务依据不同可见性规则并发执行，事务之间的依赖关系、冲突传播路径以及可接受执行结果的判定条件都会显著复杂化。现有研究虽然已经开始关注此类问题，但对于不同隔离级别事务交互时的统一语义定义、异常边界及其判定准则，尚未形成充分一致的理论框架\cite{bouajjani2025complexity}。

其次，现有研究在形式化验证层面仍存在明显不足。已有工作通常能够对特定一致性模型、特定隔离级别或局部并发控制机制进行分析与证明，但对于混合隔离级别下分布式事务系统的整体行为，尤其是跨分片事务执行过程中的状态演化、版本可见性与提交约束之间的联动关系，仍缺乏系统性的形式化表达与验证方法。这导致许多系统设计只能停留在经验性论证或局部正确性分析层面，难以对复杂并发场景下的安全属性给出严格保证。

再次，现有研究在理论模型与工程实现之间仍存在脱节。部分研究工作侧重抽象一致性公理或异常定义，能够从理论层面解释某类并发行为；另一部分工作则聚焦数据库系统实现，通过事务协调、时间戳排序、MVCC 或两阶段提交等机制提升系统性能与一致性保障能力。然而，两类研究之间缺乏稳定、清晰的映射关系，即理论模型往往难以直接指导工程实现，而工程系统中的关键机制也缺少可回溯的形式化语义支撑。这种脱节限制了研究成果的可验证性、可复现性与可推广性。

最后，现有研究对混合隔离级别系统的实验评估仍不够完整。许多工作主要围绕单一隔离级别、单类工作负载或特定系统设定展开性能测试，对不同隔离级别混合配置下系统吞吐量、事务延迟、一致性风险与扩展能力之间的关系缺乏更系统的实验分析。特别是在跨分片事务、复杂读写依赖以及多种业务负载并存的条件下，如何定量评估混合隔离级别机制在正确性与性能之间的平衡效果，仍是当前研究中的薄弱环节。

综上，当前研究虽然为分布式事务处理和一致性保障提供了重要基础，但在混合隔离级别场景下，仍然存在语义定义不统一、形式化验证不足、理论与实现衔接不紧密以及实验评估不系统等问题。因此，有必要围绕“统一语义建模、形式化正确性验证、原型系统实现与实验评估”构建一体化研究路径，以增强相关研究的严谨性、可解释性与工程可行性。

\subsection{研究挑战}
面对分布式系统和云原生架构的挑战，主流数据库产品在扩展性、可用性和运维成本方面存在一些不足。
\paragraph{传统关系型数据库}
传统关系型数据库（RDS，如 MySQL、PostgreSQL）是企业级数据存储的基石，
以其严格的 ACID 特性、强大的 SQL 查询能力和成熟的生态系统，在金融、电商等核心业务场景中占据统治地位。
但是，传统 RDS 的架构设计初衷是基于“单机”或“主从”模型，这在分布式层面带来了一些本质性的架构缺憾。

RDS 主要依赖垂直扩展（Scale-up）来提升性能，虽然通过读写分离可以扩展读能力，但在写性能扩展和海量数据存储方面存在显著瓶颈。
为了应对海量数据，RDS 通常采用分库分表（Sharding）策略，但这破坏了关系型数据库的核心优势，主要表现为：
\begin{itemize}
      \item 复杂查询受限：一旦数据被切分到不同的物理节点，跨库的 JOIN 操作、GROUP BY 聚合查询变得极其困难甚至不可用，往往需要在应用层或中间件中进行低效的数据拼装。
      \item 全局唯一性挑战：在单机环境下简单的自增主键（Auto-increment ID），在分布式环境下失效，需要引入分布式 ID 生成器（如雪花算法），增加了系统的复杂性。
\end{itemize}

同时，RDS 在分布式事务的处理上显得力不从心，尤其是对网络不稳定环境下的支持：
传统 RDS 处理跨库事务通常依赖 XA 协议（两阶段提交，2PC）\cite{Lampson1976}。
这是一个阻塞性协议，协调者需要等待所有参与者响应。
在网络不稳定的分布式环境下，XA 事务会导致严重的锁竞争和长尾延迟，系统吞吐量会随节点数增加而急剧下降\cite{Perkins2011}。

在前文中，我们提到，以MySQL和PostgreSQL为代表的关系型数据库支持了混合隔离级别（MIL）的功能，但其实现的语义是不明确且高度可变的，而且缺乏行业范围的共识或统一的正式规范。这种模糊对数据库的使用带来了不确定性。

\paragraph{Redis}
Redis 是高性能键值存储和共享缓存事实上的标准，以其亚毫秒级的响应速度著称，凭借其高性能、高可用性及易用性，已成为互联网产品中实现共享缓存的首选中间件解决方案\cite{Carlson2013}。然而，作为一款优先追求可用性（Availability）和分区容错性（Partition Tolerance）的系统，Redis集群（Cluster）在分布式强一致性和全局事务层面存在显著的架构取舍。

Redis 集群采用无中心化的分片架构，虽然实现了水平扩展，但在处理复杂分布式逻辑时面临“分片隔离”的难题：
\begin{itemize}
      \item \textbf{原子性操作无法跨越分片边界：\\}
            Redis 的事务机制（包括 Lua 脚本和 MULTI/EXEC）严格局限于单分片（Single Slot）。
            无法在同一个“事务”中对不同分片上的键进行操作。
      \item \textbf{聚合与多键操作受限：\\}
            在单机模式下极其高效的集合运算（如 SUNION、SDIFF）或批量操作（MGET），在集群模式下如果涉及多个分片的 Key，通常无法直接执行。客户端必须自行实现低效的“分散-查询-合并”逻辑，失去了 Redis 原本“计算向数据移动”的高效特性。
\end{itemize}

\paragraph{其他新型数据库}
由于分布式和云原生架构的普及，涌现出了一批新型数据库产品\cite{newsql}，它们更注重云原生、存算分离以及对分布式事务的支持程度\cite{Li2019}。

首先是支持强一致性与分布式ACID事务的NewSQL数据库\cite{Pavlo2011}。它们最显著的特点是，即使数据分布在不同的物理节点上，依然支持跨行、跨表的复杂事务的原子性操作。其中的典型代表有FoundationDB、Google Spanner 仅支持可串行化（SER），TiKV 默认采用快照隔离（SI），系统中所有事务被迫运行在同一隔离级别下，无法根据不同业务场景的需求进行动态调整。这意味着对一致性要求较低的分析类或日志类事务，也不得不承担与核心业务事务同等的同步开销，在高并发、高吞吐量的场景下性能表现不佳\cite{Bailis2014}。

从理论层面看，NewSQL 的并发控制协议（如时间戳排序、MVCC）均建立在"全局统一隔离级别"的假设之上，故此类系统在设计之初并未考虑不同隔离级别事务并发交互的场景。一旦引入混合隔离级别，不同可见性规则的事务之间的交互行为将变得难以预测，可能引发意料之外的异常，而系统本身也缺乏检测和处理此类跨级别冲突的机制。从工程层面看，这类数据库通常依赖中心节点进行事务的编排，为了保证跨分片事务的强一致性，普遍采用两阶段提交（2PC）或其变体（如 Percolator），需要多轮网络往返以达成全局共识，在高并发或跨地域部署的场景下协调延迟将成为系统性能的主要瓶颈。总体而言，NewSQL 数据库以牺牲灵活性为代价换取了强一致性保证，难以满足对性能与一致性均有差异化需求的混合业务场景。

另外还有一类数据库强调高性能与可调一致性。这类数据库通常源自 Dynamo 论文\cite{DeCandia2007}的理念，优先保证高可用性（Availability）和分区容错性（Partition tolerance），即 AP 系统。但现代版本中加入了“轻量级事务”来弥补一致性的不足。它们一般支持轻量级的事务，只能保证最终一致性\cite{Vogels2009}。其中的典型代表是Cassandra\cite{Lakshman2010}，DynamoDB\cite{DeCandia2007}等。它们在高可用性和分区容错性方面表现出色，但底层架构上的限制，导致其在实现事务处理方面存在一些不足。

综上所述，传统数据库产品在分布式系统与云原生架构下普遍面临以下挑战：其一，如何在跨节点事务处理中兼顾可扩展性、执行效率与实现复杂度；其二，如何在不同业务负载并存的场景下，使事务在要求的隔离级别下成立，同时避免单一强隔离策略带来的过高性能开销；其三，如何为混合隔离级别场景建立严谨、可验证且可实现的统一语义框架。围绕上述挑战，构建兼顾理论严谨性与工程可行性的分布式键值数据库系统，具有明确的研究价值与实际意义。

\section{本文的主要工作与不足}
本文采用分片（Sharding）架构\cite{thomson2012calvin}，参考 MongoDB 的设计，将数据水平切分并分布存储在多个物理节点上，从而实现存储容量与处理能力的水平扩展。系统包含路由节点（Router）作为客户端请求的统一入口，负责根据分片键将读写请求分发到对应的数据节点；同时引入配置节点（Config Server）维护全局元数据和分片映射关系。在此基础上，本文围绕混合隔离级别下跨分片事务处理的语义定义、正确性验证与系统实现展开研究。

本文的主要工作如下：
\begin{itemize}
      \item 面向分布式键值数据库场景，构建了混合隔离级别事务处理的形式化描述框架，明确了不同隔离级别事务并发执行时的可见性规则、冲突约束与异常边界。
      \item 设计了支持混合隔离级别的分布式事务操作语义，并给出了与系统实现相对应的关键状态转换与并发控制机制。
      \item 使用 \TLAPlus 与 TLC 对事务操作语言、一致性公理和隔离级别约束进行形式化建模与模型检查，验证系统在要求的隔离级别下成立。
      \item 设计并实现了一个支持混合隔离级别的分布式键值数据库原型系统，完成了路由、分片、MVCC、HLC、跨分片事务协调及可观测性模块的工程实现。
      \item 通过基准实验评估不同隔离级别配置下的系统吞吐量与延迟表现，说明混合隔离级别机制在保证事务在要求的隔离级别下成立的前提下，能够有效提升系统整体执行效率。
\end{itemize}

尽管本文完成了从理论到原型系统的较完整研究，但仍存在以下不足：
\begin{itemize}
      \item 本文原型系统主要面向分布式键值数据库场景展开设计与验证，对于复杂查询优化、二级索引及多模型数据支持等问题涉及较少，系统能力仍有进一步扩展空间。
      \item 形式化模型聚焦于混合隔离级别下事务语义与核心并发控制机制，对故障恢复、节点动态扩缩容以及副本复制等工程细节进行了必要抽象，尚未覆盖完整生产环境中的全部复杂因素。
      \item 实验评估主要验证了不同隔离级别配置下的吞吐量与延迟变化，对超大规模集群、跨地域部署以及更多真实业务负载模式下的长期稳定性研究仍有待进一步开展。
\end{itemize}

\section{本文的组织结构}
第一章为绪论，主要介绍研究背景与研究意义，分析相关研究现状与面临的关键挑战，并概述本文的主要工作、不足与组织结构。

第二章为相关技术与理论，介绍数据库异常与隔离级别、一致性建模基础以及 \TLAPlus 与 TLC 等形式化验证相关技术，为后续章节奠定理论基础。

第三章讨论系统操作语义，从系统架构、混合逻辑时钟与事务操作语义三个方面给出支持混合隔离级别的分布式事务执行模型。

第四章围绕事务操作语言的 \TLAPlus 表达、一致性公理与隔离级别约束以及模型检查实验与结果展开，对第三章提出的操作语义进行形式化验证。

第五章介绍原型系统的架构设计与系统实现，重点说明关键模块的设计目标、实现机制与工程落地方式。

第六章通过实验验证混合隔离级别机制对系统性能的提升效果，分析不同部署拓扑与不同隔离级别配置下的吞吐量表现。

第七章对全文工作进行总结，并展望未来的研究方向。
