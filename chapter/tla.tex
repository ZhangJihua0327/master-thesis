\subsection{\TLAPlus 形式规约语言}

\TLAPlus\footnote{\url{https://lamport.azurewebsites.net/tla/tla.html}}是由图灵奖得主 Leslie Lamport 主导开发的一种高级规约语言，基于动作时序逻辑（Temporal Logic of Actions, TLA）\cite{Lamport1994}。它在计算机程序和系统建模领域具有广泛应用\cite{newcombe2014use,vergamini1988verification,hackett2023understanding}，尤其适用于对并发系统和分布式系统进行建模。\TLAPlus 的设计理念是使用简洁的数学语言来精确描述系统的行为。因此，它的表达方式不同于传统的编程语言，而更贴近数学语言的严谨性。\TLAPlus 本质上不是一种用于执行的编程语言，而是一种规约语言（Specification Language）。它不关注协议或系统的底层实现细节，而是允许开发者从更高的抽象层次审视程序的整体设计。因此，\TLAPlus 及其配套工具在排查和消除分布式系统中极难发现且纠错成本高昂的并发逻辑错误方面，发挥着不可替代的作用。

需要指出的是，\TLAPlus 旨在帮助规约开发者更好地表达协议或系统的设计，而非专门为寻找归纳不变式（Inductive Invariants）而设计。尽管如此，凭借其丰富的语法、直观的表达方式以及在工业界的广泛应用，\TLAPlus 在自动化生成归纳不变式的研究领域同样展现出了广阔的应用前景。

开发者使用 \TLAPlus 或其他形式化工具对分布式协议进行建模的代码，通常被称为“规约”（Specification，简称 spec）。图 \ref{fig:client_server} 展示了一个简明的 \TLAPlus 规约示例，其描述了一个基础的客户端-服务器通信协议。在该规约中，有两个至关重要的谓词（Predicate）：$Init$ 和 $Next$。$Init$ 定义了系统的初始状态，描述系统启动时的基本配置；而 $Next$ 定义了系统的状态转移关系，即系统在经历一个时间步后状态将如何演进。此外，谓词 $Safe$ 作为安全属性（Safety Property），是验证的核心。一个正确建模的分布式协议规约，必须确保在所有可达状态下严格满足该安全属性，这一变量在自动化归纳不变式的研究中占据关键地位。同时，该规约中还包含如 $Connect$ 和 $Disconnect$ 等动作定义，这类似于编程语言中的函数，极大提升了规约的可读性与复用性。部分规约还会引入 $TypeOK$ 谓词，用于实施类型约束。在自动归纳不变式生成研究中常用的另一款工具 IVy，也采用了类似的模型结构。由此可见，\TLAPlus 聚焦于系统的状态空间及其转移逻辑，抽象了具体的执行过程，这种基于状态机的描述范式使其能够精准捕捉分布式系统的复杂并发行为。

TLC 是 \TLAPlus 工具链中集成的模型检查器。除了 TLC，\TLAPlus Toolbox 还集成了 PlusCal（一种更接近伪代码的模型语言）、用于定理证明的 TLAPS、用于语法分析的 SANY，以及用于规约美化排版的 \LaTeX 渲染工具。由于这些辅助工具与本文核心讨论的内容关联较弱，此处不作详细展开。

本文所设计的验证架构只接受原生 \TLAPlus 规约。

\subsection{TLC模型检查器}\label{sec:tlc-apalache}
TLC 既是针对 \TLAPlus 规约的模型检查工具，也可作为规约的模拟器。它是一个显式状态模型检查器（Explicit-State Model Checker），根据用户提供的规约及配置参数，穷举搜索所有满足约束的可达状态及其转移路径。在搜索过程中，TLC 会实时验证状态是否始终满足安全属性及其他用户定义的逻辑谓词。一旦发现违背属性的错误，TLC 会输出详细的错误状态序列（Error Trace），帮助开发者快速定位并分析缺陷原因。

为了加速模型检查，TLC 可以利用超过 32 个计算线程实现近乎线性的性能提升。此外，TLC 还支持在分布式计算集群上运行以进一步加速状态空间的探索，并提供了便捷的云环境部署方案。

\section{基于 \TLAPlus 的混合隔离级别验证架构}

在前文中，我们已经介绍了 \TLAPlus 规约语言及 TLC 模型检查器的基础概念与设计范式。

在本节中，我们将详细阐述如何利用 \TLAPlus 构建一个针对混合隔离级别操作语义的严格验证架构，完整的模型代码参见附录~\ref{app:tla}。基于前文构建的一致性理论，该形式化代码主要划分为两部分：第一部分为事务操作语义的精确状态机建模；第二部分为一致性公理与特定隔离级别约束条件的逻辑定义。
\subsection{事务操作语义}
\subsubsection{状态模型}

定义操作语义的第一步是定义状态模型。我们使用一个状态变量来表示系统的当前状态，这个状态变量可以包含多个组件，例如事务的状态、数据项的值、锁的状态等。通过定义这些组件，我们可以准确地描述系统在任意时刻的状态。

重要的变量有：
\begin{itemize}
    \item \texttt{store}: 全局键值存储，模拟数据库的持久化状态。它是一个映射，键是 Keys，值是版本历史（包含值、提交时间戳 cts、写入者）。
    \item \texttt{tx\_buffer}: 事务的本地写缓冲，模拟事务在提交前对数据的本地修改。
    \item \texttt{tx\_snapshot}: 事务的读取快照版本，决定了事务能看到哪些数据。
    \item \texttt{op\_seq}: 记录操作的历史序列，用于后续的公理化验证。
\end{itemize}

通过以上变量，我们可以构建一个完整的状态模型，准确地描述系统在状态。在这样的基础上，我们可以继续形式化地描述操作语义。

\subsubsection{核心状态转换动作 (Transition Actions)}
操作语义的核心逻辑封装在三个主要的 \TLAPlus  动作定义中：

\textbf{A. 事务开始 ($StartTx(t)$)}

形式化描述了事务如何获取其读取视图（Read View）：
\begin{itemize}
    \item 根据事务的隔离级别 ($Workload[t].level$)，决定 $tx\_snapshot[t]$ 的值。
    \item 例如：SI (Snapshot Isolation) 获取当前的全局 $shard\_ct$（时间戳）。
    \item RA (Read Atomicity) 获取客户端上一次提交的时间 $client\_last\_commit$。
    \item 将事务状态 $tx\_status$ 设为 "Active"。
\end{itemize}

\textbf{B. 执行操作 ($ExecuteOp(t)$)}

这是读写操作的具体语义描述。它根据 $Workload$ 中预定义的操作类型进行分支：

\begin{enumerate}
    \item \textbf{读操作 ($op.type = "R"$):}
          \begin{itemize}
              \item \textbf{本地优先读取:} 首先检查 $tx\_buffer[t][op.key]$（即写后读 Read-Your-Writes 语义）。
              \item \textbf{快照读取:} 如果本地没有，则调用辅助算子\\ $MaxVersion(store[op.key], tx\_snapshot[t])$。这意味着它会在全局存储的版本历史中，找到提交时间戳小于等于事务快照的最新版本。
              \item \textbf{记录历史:} 将读取结果追加到 $op\_seq$，用于验证。
          \end{itemize}
    \item \textbf{写操作 ($op.type = "W"$):}
          \begin{itemize}
              \item \textbf{写缓冲:} 并不会立即修改全局 $store$，而是更新 $tx\_buffer$。
              \item \textbf{记录历史:} 将写操作追加到 $op\_seq$。
          \end{itemize}
\end{enumerate}

\textbf{C. 提交事务 ($CommitTx(t)$)}

形式化描述了提交协议，包括并发控制和原子性：

\begin{enumerate}
    \item \textbf{冲突检测 ($HasConflict$):}
          \begin{itemize}
              \item 定义了谓词 $IsConcurrent(t\_other)$ 来识别并发事务。
              \item 检查是否存在其他并发已提交的事务，其写入集（Writes）与当前事务的检查集（Checkset/ReadSet）有冲突。这对应了乐观并发控制（OCC）的验证阶段。
          \end{itemize}
    \item \textbf{状态更新:}
          \begin{itemize}
              \item \textbf{Abort:} 如果有冲突，状态变为 "Aborted"。
              \item \textbf{Commit:}
                    \begin{itemize}
                        \item 递增全局时间戳 $shard\_ct$。
                        \item \textbf{原子写入:} 将 $tx\_buffer$ 中的数据合并到全局 $store$ 中，生成带有新时间戳的新版本。
                        \item 更新客户端依赖 $client\_dep$。
                    \end{itemize}
          \end{itemize}
\end{enumerate}

不同于面向具体业务逻辑的程序语言，\TLAPlus 的代码更关注的是状态转移的结果，在运行\TLAPlus 代码时，TLC 模型检查器会穷举所有可能的状态转移路径，并检查在这些路径上是否满足定义的安全属性。通过定义不同的安全属性，我们就可以验证系统在不同隔离级别下是否满足这些属性，从而验证系统的正确性。

\subsection{测试方式和测试结果}

测试用例只需通过 \texttt{INSTANCE MixedIsolation WITH ...} 语法注入负载，引擎即可启动运转。在进行验证时，TLC 模型检查器探索所有通过 \texttt{Next} 产生的合法状态转移路径。TLC 的穷举能力确保了网络延迟、乱序提交与快照交错情形都将被覆盖。一旦发现在某个微观并发下，生成的图违反了 \texttt{OperationalSafety == IsConsistentExecution} 断言，就会停止并抛出精准的反例路径追踪报告（Error Trace File），协助开发者定位修缮并发漏洞。

附录~\ref{app:example} 展示了一个针对 SmallBank 负载的测试用例。通过注入 SmallBank 负载，TLC 模型检查器能够验证在该负载下系统是否满足定义的安全属性，并且能够发现潜在的并发问题。
通过测试可以看到，在 SmallBank 负载下，系统满足定义的安全属性，并且没有发现潜在的并发问题。这表明在该负载下，系统的操作语义是正确的，并且能够满足一致性要求。

图~\ref{fig:tla_bash} 展示了 TLC 模型检查器的终端输出示例，其中包含了模型检查的进度、状态生成和发现的状态数量，以及最终的检查结果。通过测试结果可以知道，TLC 模型检查器成功地完成了模型检查，并且没有发现任何违反安全属性的状态。这表明在 SmallBank 负载下，系统的操作语义是正确的，并且能够满足一致性要求。

按照同样的方式，我们可以在众多测试集合中进行测试，验证当前操作语义满足定义的安全属性，并且没有发现潜在的并发问题。这表明在这些负载下，系统的操作语义是正确的，并且能够满足各个事务的一致性要求。

\section{本章小结}

本章详细介绍了利用 \TLAPlus{} 形式化规约语言及其模型检查工具TLC，对分布式事务系统操作语义进行精确建模与验证的方法。首先介绍了基本概念与TLC模型检查器工作原理。其次构建了基于 \TLAPlus{} 的混合隔离级别验证架构，形式化描述了事务状态转换逻辑并转化一致性公理为 \TLAPlus{} 谓词。最后通过SmallBank负载测试案例展示了TLC基于该模型验证一致性的能力，有力地证明了操作语义设计的正确性，为系统工程实现提供了可靠的理论保障。
