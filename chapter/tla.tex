\chapter{支持混合隔离级别机制的\TLAPlus 建模与验证}

\section{事务操作语义的\TLAPlus 表达}

第二章已经介绍了 \TLAPlus 与 TLC 的基本概念。本章在此基础上进一步面向本文提出的事务模型，给出事务操作语义的 \TLAPlus 表达方式。形式化规约仍采用“初始状态 $Init$ + 状态转移 $Next$ + 安全断言”的组织范式，但其中涉及的状态变量、动作定义与约束条件均围绕混合隔离级别事务的执行过程展开。

在状态建模上，本文将事务执行过程抽象为一个离散状态机。系统状态不仅包含全局键值存储及其版本历史，还包含事务缓冲区、事务快照、操作历史以及客户端依赖信息等辅助变量。通过这种建模方式，系统在任意执行时刻的可见状态都能够被形式化描述，从而为后续公理的检查提供统一的语义基础\footnote{项目模块代码提供在 \url{https://github.com/ZhangJihua0327/mil-tla-verify} 仓库中。}。

\section{公理和隔离级别约束}

在前文中，本文已经介绍了 \TLAPlus 规约语言及 TLC 模型检查器的基本概念与设计范式。

在本节中，本文进一步说明如何利用 \TLAPlus 构建一个面向混合隔离级别操作语义的严格验证框架。在这一框架下，形式化约束的构造主要包括两个方面：其一是将事务执行历史转化为抽象执行中的 $\text{VIS}$ 与 $\text{AR}$ 关系；其二是将一致性公理与隔离级别约束转化为可由 TLC 检查的逻辑断言。
\subsection{状态变量与动作定义}
\subsubsection{状态模型}

定义操作语义的第一步是构造状态模型。本文使用一组状态变量来表示系统的当前状态，这些变量共同描述事务状态、数据项取值、版本可见性以及相关依赖关系。通过对这些组件作出明确约束，可以较为准确地刻画系统在任意时刻的运行状态。

重要的变量有：
\begin{itemize}
    \item \texttt{store}: 全局键值存储，模拟数据库的持久化状态。它是一个映射，键是 Keys，值是版本历史（包含值、提交时间戳 cts、写入者）。
    \item \texttt{tx\_buffer}: 事务的本地写缓冲，模拟事务在提交前对数据的本地修改。
    \item \texttt{tx\_snapshot}: 事务的读取快照版本，决定了事务能看到哪些数据。
    \item \texttt{op\_seq}: 记录操作的历史序列，用于后续的公理化验证。
\end{itemize}

通过上述变量，可以构建一个较为完整的状态模型，并据此进一步形式化描述事务操作语义。

\subsubsection{核心状态转换动作 (Transition Actions)}
操作语义的核心逻辑可归纳为三个主要的 \TLAPlus 动作定义，分别对应事务开始、操作执行与事务提交三个阶段。三类动作并不是彼此孤立的局部规则，而是共同构成了事务从建立可见快照、逐步消费操作序列，到最终完成校验与提交的完整状态演化过程。按照这一顺序展开说明，不仅能够更清楚地呈现模型中的状态转移链条，也有助于解释这些动作如何共同支撑后续的一致性公理验证。

\TopicTitle{A. 事务开始 ($StartTx(t)$)}

$StartTx(t)$ 形式化描述了事务获取读取视图（Read View）的过程。该动作首先根据事务的隔离级别 $Workload[t].level$ 为 $tx\_snapshot[t]$ 赋值，再将事务状态 $tx\_status$ 更新为 ``Active''，从而使事务进入可执行状态。不同隔离级别对应不同的快照来源：SI（Snapshot Isolation）直接读取当前全局提交时钟 $shard\_ct$，RA（Read Atomicity）则继承客户端最近一次提交时间 $client\_last\_commit$。更一般地说，PC、SI 和 SER 从全局提交时钟获取一致快照，CC 与 PSI 继承会话依赖，而 RA 仅依赖客户端最近一次提交时间。由此可见，事务在开始阶段绑定的快照来源不同，后续读操作可访问的版本边界也随之不同。换言之，不同隔离级别在可见性上的差异，在模型中首先体现为事务启动阶段对快照来源的不同选择。

\TopicTitle{B. 执行操作 ($ExecuteOp(t)$)}

$ExecuteOp(t)$ 给出了读写操作的具体语义，并依据 $Workload$ 中预定义的操作类型进行分支。对于读操作，模型首先检查本地写缓冲 $tx\_buffer[t][op.key]$，从而保证事务内部满足 Read-Your-Own-Writes 语义；若本地不存在对应写入，则调用辅助算子 $MaxVersion(store[op.key], tx\_snapshot[t])$，从全局存储的版本历史中选取提交时间戳不超过事务快照的最新版本，并将读取结果追加到 $op\_seq$ 以供后续验证。对于写操作，模型并不立即修改全局 $store$，而是先将结果写入 $tx\_buffer$，同时将该写操作记录到 $op\_seq$ 中。这里需要强调的是，读操作和写操作在模型中承担的并不是对称职责：前者负责在“局部写集”和“快照可见版本”之间解析事务当前可读到的值，后者则负责积累尚未提交的局部更新，为提交阶段的原子写入预先组织好输入。这样的定义保留了两个最关键的语义点：一是事务内部的本地优先读取，二是基于快照上界的版本选择。由此，版本可见性被归约为一个可由 TLC 直接枚举和检查的选择过程，同时也使本地缓冲与全局版本历史之间的分工更加清晰。

\TopicTitle{C. 提交事务 ($CommitTx(t)$)}

$CommitTx(t)$ 则形式化描述了提交协议，其中同时包含并发控制与原子性要求。模型首先通过 $HasConflict$ 执行冲突检测，并借助谓词 $IsConcurrent(t\_other)$ 识别与当前事务并发的已提交事务；若存在其他事务的写入集与当前事务的检查集（Checkset/ReadSet）发生交叉，则说明乐观并发控制（OCC）的验证失败，此时事务状态被更新为 ``Aborted''。若冲突检测通过，模型便进入提交路径：一方面递增全局时间戳 $shard\_ct$，另一方面将 $tx\_buffer$ 中的数据以原子方式合并到全局 $store$，生成带有新时间戳的版本，并同步更新客户端依赖 $client\_dep$。这一设计的关键之处在于，它将“是否允许事务提交”和“提交后如何改变全局状态”放在同一个动作中统一处理，从而避免把语义上应当同时成立的步骤拆散为多个松散的状态变化。在这一阶段，模型通过 \texttt{HasConflict} 谓词统一表达 PSI、SI 与 SER 等隔离级别所需的并发校验，并以单个状态跃迁完成提交时间分配与新版本写入。由于 \TLAPlus 以状态转移为核心，上述定义能够将“冲突检测”与“原子提交”纳入同一条可验证路径，从而避免在正文中展开与证明主线关系不大的工程性细节，也使提交阶段的形式化表达更接近实际系统中的整体提交语义。

这里的核心思想是将事务历史中的可见性关系与仲裁关系明确写成可检验的形式化对象，使前文给出的一致性公理不再停留于抽象的数学关系层面，而能够与模型检查中的状态约束形成一一对应。

在定义抽象执行 $\mathcal{X}$ 之后，还需要进一步对公式~\ref{eq:consistency} 中的公理进行形式化表达，才能将前文给出的数学定义真正落实为 TLC 可检查的逻辑约束。换言之，若说 $\text{VIS}$ 与 $\text{AR}$ 给出了事务历史的结构，那么这些公理所描述的就是该结构必须满足的合法性条件。图~\ref{fig:axioms} 展示了这些公理的形式化表达；在此基础上，便可进一步定义不同隔离级别对应的约束，并把“抽象一致性要求”转化为“模型检查中的可判定性质”。

图~\ref{fig:axioms} 中各项公理并不是彼此孤立的局部条件，而是与前述的 $\text{VIS}$ 和 $\text{AR}$ 关系共同构成完整的抽象执行约束。也正因为如此，模型验证并不是单纯检查某个局部谓词是否成立，而是检查整个执行历史是否同时满足可见性关系、仲裁顺序以及一致性公理之间的联合约束。

不同于面向具体业务逻辑的程序语言，\TLAPlus 更关注状态转移结果本身。运行 \TLAPlus 代码时，TLC 模型检查器会穷举所有可能的状态转移路径，并检查这些路径是否满足预先定义的安全属性。通过配置不同的安全属性，便可以验证系统在不同隔离级别下是否满足相应约束，从而验证模型设计的正确性。

\section{模型检查实验与结果}

测试用例通过 \texttt{INSTANCE MixedIsolation WITH ...} 语法注入负载，验证引擎即可启动运行。本文用于验证的负载来自 Courseware、SmallBank 和 TPCC 三类基准场景中已经分配隔离级别的工作负载，每组负载包含事务类型、事务所属隔离级别、读写操作序列以及访问键集合等信息。模型检查时，这些负载被转换为 \TLAPlus 模块中的常量，使 TLC 能够按照操作语义枚举不同事务操作之间的交错执行路径。

验证的核心判定目标是操作语义生成的运行历史（History）是否一致。在验证过程中，TLC 模型检查器会探索所有通过 \texttt{Next} 产生的合法状态转移路径，并记录事务开始、读、写、提交和中止等操作组成的 \texttt{op\_seq}。随后，模型根据该运行历史构造抽象执行关系，包括事务可见性关系 $\mathrm{VIS}$ 与仲裁顺序 $\mathrm{AR}$，并检查安全断言 \texttt{OperationalSafety == IsConsistentExecution}。若 History 中所有事务在其对应隔离级别下均满足第二章定义的公理约束，则该 History 被判定为一致；反之，只要存在某个事务违反其隔离级别约束，TLC 即会停止搜索并输出反例路径追踪报告（Error Trace File），用于定位导致不一致的具体操作交错。

\section{本章小结}

本章围绕支持混合隔离级别机制的 \TLAPlus 建模与验证展开。首先给出了事务操作语义的 \TLAPlus 表达方式，说明状态变量与核心动作如何共同描述事务执行过程；其次构建了抽象执行关系、一致性公理与隔离级别约束的形式化断言；最后结合模型检查实验及结果分析，验证了本文所设计的操作语义能够保证事务满足目标隔离级别的要求，并为后续原型系统实现提供形式化依据。
