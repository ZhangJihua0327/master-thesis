\chapter{分布式键值数据库原型的架构设计与实现}
本章将基于前序章节中关于分布式数据库的建模和分析，以及经\TLAPlus 验证过的支持混合隔离级别的分布式数据库操作语义，设计并实现一个数据库原型系统，用于验证该操作语义相较于只支持单一隔离级别的操作语义在性能上的优势。

\section{原型系统概述}
前文提出的事务操作语义与并发控制机制，最终需要落到可运行的系统中才能检验其可行性。基于这一点，本文实现了一个分布式键值数据库原型。该原型由路由节点、配置节点和分片节点组成，支持多版本并发控制、跨分片事务协调以及多种隔离级别的混合执行。它并不以产品化为目标，而是作为研究载体，用于验证核心机制能否落地实现，并为后续实验提供可重复的运行环境。

具体来说，该原型主要承担三项工作：验证第三章提出的系统操作语义能否转化为可执行机制，检验第四章中的形式化约束能否与关键模块设计保持一致，以及通过实验比较不同隔离级别配置下的吞吐量与回滚率表现。基于这一定位，本章先说明系统需求与实现边界，再展开架构设计和关键模块实现。

需要说明的是，第二章和第三章中的 RA、CC、PC、PSI、SI 和 SER 构成本文统一公理化模型下的理论范围，而本章原型系统选择实现 PC、PSI、SI 和 SER 四种隔离级别，主要是出于工程验证目标与系统机制覆盖范围的考虑。RA 是公理体系中的基础级别，其核心约束主要由事务内部读写规则、已提交版本读取和会话顺序维护保证，在本文原型的 MVCC 与事务缓冲机制中已作为更高隔离级别的公共基础被隐含满足，因此未作为独立可配置级别展开实验。同时，RA 和 CC 均属于约束相对较少的弱隔离级别，能够提供的异常排除能力有限，在现实数据库系统中作为独立事务隔离选项的应用场景相对较少。特别是在本文关注的混合隔离场景下，若将大量事务下放到 RA 或单独的 CC，虽然可能进一步降低协调开销，但其语义保障过弱，难以代表工程系统中常见的正确性与性能折中。CC 强调因果依赖传播，而 PSI 已在 CC 的基础上进一步加入写冲突约束，能够同时覆盖依赖传播机制与冲突认证机制的组合效果；本文实验重点又在于比较前缀快照、写冲突认证以及可串行化检查等机制对系统性能的影响。因此，工程实现中的四种级别并不是对理论模型范围的收缩，而是在六类理论级别中选取更能体现系统协调代价差异、业务语义保障强度和实验对比价值的代表性子集。

\section{需求分析}
该原型的设计目标比较明确：在保证目标事务语义的前提下，观察混合隔离级别执行相较于统一隔离级别方案是否具有性能优势。围绕这一目标，下面从功能需求和非功能需求两个方面说明系统需要具备的能力。

\subsection{功能需求}
功能需求定义了系统必须完成的具体任务和行为。基于验证混合隔离级别性能优势的目标，系统的主要功能需求如下：

\begin{enumerate}
      \item \textbf{基本数据操作}：本原型系统作为一个键值（Key-Value）数据库，需支持基本的读（Get）、写（Put）、增（Insert）、删（Delete）四种数据操作。数据模型以键值对（Key-Value）形式存储，不支持复杂的嵌套文档结构。
      \item \textbf{分布式集群管理}：
            \begin{itemize}
                  \item \textbf{分片（Sharding）}：支持将数据水平切分并分布在多个分片节点上。
                  \item \textbf{路由（Routing）}：客户端通过路由节点访问数据，路由节点根据分片键将请求转发至正确的分片。
            \end{itemize}
      \item \textbf{事务管理}：
            \begin{itemize}
                  \item \textbf{事务生命周期}：支持事务的开启（Start）、提交（Commit）和中止（Abort）。
                  \item \textbf{跨分片事务}：支持涉及多个分片的分布式事务，保证原子性。
            \end{itemize}
      \item \textbf{混合隔离级别支持}：这是本系统的核心需求。系统允许客户端在开启事务时指定该事务的隔离级别。系统应至少支持以下几种隔离级别的混合运行：
            \begin{itemize}
                  \item \textbf{前缀一致性（Prefix Consistency, PC）}
                  \item \textbf{并行快照隔离（Parallel Snapshot Isolation, PSI）}
                  \item \textbf{快照隔离（Snapshot Isolation, SI）}
                  \item \textbf{可串行化（Serializable，SER）}
            \end{itemize}
            系统需要确保在上述隔离级别混合运行时，事务能够在要求的隔离级别下成立，并保证系统行为与形式化语义保持一致。
\end{enumerate}

\subsection{非功能需求}
非功能需求涉及系统的性能、可靠性等方面：
\begin{enumerate}
      \item \textbf{高性能}：由于采用了全内存存储，系统应具有较低的读写延迟和较高的吞吐量。
      \item \textbf{可扩展性}：系统应支持水平扩展，通过增加分片节点来线性提升存储和处理能力。
      \item \textbf{可观测性}：为了验证性能优势，系统必须提供详细的性能监控指标（如延迟、吞吐量、冲突率等），以便进行后续的实验对比。
\end{enumerate}

\subsection{用例分析}
系统主要涉及两类角色：客户端用户（Client）和系统管理员（Admin）。
\begin{itemize}
      \item \textbf{客户端用户}：主要进行数据的读写操作和事务处理。他们可以发起普通读写请求，也可以开启特定隔离级别的事务进行一系列操作。
      \item \textbf{系统管理员}：负责集群的配置，如添加分片、配置路由规则等。
\end{itemize}

\section{系统设计}
基于上述需求分析，本节将对数据库原型系统进行总体架构设计和模块设计。

\subsection{总体架构设计}
本系统采用经典的 Shared-nothing 分布式架构\cite{dewitt1992parallel}，参考 MongoDB 的集群模型，主要由三类组件构成：路由节点（Router）、配置节点（Config Server）和分片节点（Shard Server）。
整体组件关系如图~\ref{fig:architecture} 所示。

\begin{figure}[htbp]
      \centering
      \includegraphics[width=0.9\textwidth]{figures/mmd/architecture.pdf}
      \caption{系统总体架构图}
      \label{fig:architecture}
\end{figure}

各组件职责如下：
\begin{itemize}
      \item \textbf{路由节点（Router）}：
            作为集群的统一入口，对外提供以 MySQL 或自定义协议的接口。
            路由节点不存储实际数据，只缓存元数据（Metadata）。
            它负责解析客户端请求，根据分片键（Shard Key）和路由表（Routing Table）将请求路由到具体的分片节点。
            对于跨分片事务，路由节点充当事务协调者（Coordinator）的角色，负责两阶段提交（2PC）的协调工作。

      \item \textbf{配置节点（Config Server）}：
            存储集群的元数据，包括分片信息、路由表规则、节点状态等。
            保证元数据的高可用和强一致性是配置节点的关键，但在本原型中，为了简化实现，可采用单点或简单的副本机制。

      \item \textbf{分片节点（Shard Server）}：
            负责实际数据的存储和操作执行。
            每个分片节点维护一部分数据，并包含本地的事务执行引擎和存储引擎。
            分片节点作为分布式事务的参与者（Participant），响应协调者的指令，并负责本地数据的并发控制（Concurrency Control）。
\end{itemize}

\subsection{核心模块设计}

\subsubsection{存储引擎设计}
为了简化实现并聚焦于并发控制机制的验证，本原型采用全内存存储引擎。数据在内存中以键值对（Key-Value）的形式组织。为了支持多版本并发控制（MVCC），每个键对应的值不仅仅是单一数据，而是一个版本链（Version Chain）。
\begin{itemize}
      \item \textbf{多版本数据结构}：每个数据项包含多个版本，每个版本携带创建该版本的事务时间戳（Commit Timestamp）和实际数据载荷。
      \item \textbf{内存索引}：使用哈希表（Hash Map）或 跳表（Skip List）作为索引结构，实现 $O(1)$ 或 $O(\log N)$ 的快速查找。
\end{itemize}

\subsubsection{事务管理模块设计}
事务管理模块是系统的核心，分为协调者模块（位于 Router）和参与者模块（位于 Shard）。

\begin{enumerate}
      \item \textbf{混合逻辑时钟（HLC）}：
            系统采用 HLC 作为时间源。HLC 提供了单调递增的时间戳，用于定序事务和版本控制。

      \item \textbf{并发控制协议}：
            为了支持混合隔离级别，系统采用基于时间戳的 MVCC 协议。
            \begin{itemize}
                  \item 对于 \textbf{Prefix Consistency (PC)} 事务，读取全局仲裁序列某个一致前缀上的可见版本，避免观察到带“空洞”的历史。
                  \item 对于 \textbf{Parallel Snapshot Isolation (PSI)} 事务，允许在不同的分片上读取到不同快照的数据，但在同一分片上满足 SI。
                  \item 对于 \textbf{Snapshot Isolation (SI)} 事务，在事务开始时获取快照时间戳（StartTS），读取 CommitTS $\le$ StartTS 的最新版本。
                  \item 对于 \textbf{Serializable (SER)} 事务，除了遵循 SI 的读规则外，还需进行冲突检测（如写偏斜检测），确保可串行化。
            \end{itemize}

      \item \textbf{分布式事务原子性}：
            采用两阶段提交（2PC）协议。
            \begin{itemize}
                  \item \textbf{Prepare 阶段}：协调者向所有参与者发送 Prepare 请求，参与者执行本地事务逻辑，锁定资源，并持久化（在内存中模拟）事务意向。
                  \item \textbf{Commit/Abort 阶段}：如果所有参与者 Prepare 成功，协调者发送 Commit，否则发送 Abort。
            \end{itemize}
\end{enumerate}

\subsubsection{通信模块设计}
节点间通信采用异步 I/O 模型（如 RPC 或 TCP 长连接），以减少网络通信开销。消息定义采用 Protobuf 等序列化格式，确保高效传输。

\section{系统实现}
\subsection{存储分片与分布式事务}

在原型系统中，分片（Shard）既负责数据的物理存储，也承担事务执行过程中的版本管理与隔离级别约束。系统通过 \lstinline|shard| 包下的 \lstinline|Shard| 结构体封装分片状态机。本小节主要说明四部分实现：分片内事务信息的组织方式、基于 MVCC 的读写流程、两阶段提交中的可见性漏洞修复，以及单分片事务的快速提交优化\footnote{本文的代码提供在仓库 \url{https://github.com/ZhangJihua0327/let-mil-go} 中。}。

\subsubsection{事务操作信息的分层与局部化管理}
本系统采用了“全局协调计算，局部状态下推”的事务信息管理范式。在事务生命周期初始化阶段（\lstinline|TxStart|），事务的全局元数据（如事务ID、隔离级别和全局快照时间戳 \lstinline|snapshotTime|）由协调者（Router）统一获取并下发。这种设计能够让不同分片共享同一个全局时间基准，进而支持前缀一致性（PC）、快照隔离（SI）以及严格可串行化（SER）。图~\ref{fig:global-timeline} 展示了全局事务信息的分发与下推流程，协调者在事务开始时通过 RPC 将全局元数据广播至所有相关分片，确保每个参与者节点都能基于同一时间线进行版本控制和并发调度。


\begin{figure}[htbp]
      \centering
      \includegraphics[width=0.9\textwidth]{figures/mmd/global-timeline.pdf}
      \caption{组件交互时序图}
      \label{fig:global-timeline}
\end{figure}

相对地，涉及具体分片的数据操作信息由分片内的 \lstinline|TxBufferManager| 进行局部维护。考虑到未决事务的读写集可能带来较高的内存开销，代码在此采用了懒加载（Lazy Load）机制：只有当该分片真正执行首次 \lstinline|TxRead| 或 \lstinline|TxWrite| 时，才会实例化对应事务的局部缓存（\lstinline|TxBuffer|）。这种分阶段存储方式减少了无效状态分配，也使事务状态更多保留在实际参与执行的分片上。

\subsubsection{基于MVCC引擎的多版本读写流转}
分片底层的无锁化读并发依赖于多版本并发控制（MVCC）模型。以 \lstinline|TxRead| 为例，代码在读取数据时，严格遵循“读己之所写（Read-Your-Own-Writes）”的内部一致性：系统首先探测本地事务缓冲区的 Write 集合，命中后判断记录是否带有删除标记（Deleted）。如果本地无修改记录，读请求将穿透至底层的 \lstinline|MVCCStore| 操作对象，基于给定的 \lstinline|snapshotTime| 定位并获取小于但最接近该时钟的可用历史版本。

此外，程序还为最高隔离级别（SER）引入了悲观的锁机制转换。如果事务的隔离级别为 SER，分片内部将直接通过 \lstinline|lockMgr.AcquireRead| 强制索取分布式共享锁，在读写阶段即时屏蔽幻读和写倾斜缺陷，从而保证全局事务的严格串行化调度。

\subsubsection{两阶段提交可见性漏洞(Hole)的消除}
在标准的分布式两阶段提交（2PC）协议中，由于多个参与者节点的 \lstinline|Prepare| 阶段无法做到绝对原子同频，常存在所谓的可见性漏洞（Visibility Hole）——即事务虽然已经预定将要提交，但若并发的读取操作携带了更大（或相同）的时间戳进入，可能会因为读取到旧版本而破坏线性一致性。

\begin{figure}[htbp]
      \centering
      \includegraphics[width=0.9\textwidth]{figures/mmd/2pc-hole.pdf}
      \caption{两阶段提交可见性漏洞示意图}
      \label{fig:2pc-hole}
\end{figure}

图~\ref{fig:2pc-hole} 展示了本组件处理两阶段提交可见性漏洞的方式。系统借助未决状态（Pending Status）与时间戳推进来约束该阶段的可见性：在 \lstinline|Prepare| 阶段，系统根据混合逻辑时钟（HLC）派生本地的预备时间 \lstinline|prepareTime|。此时系统并不直接覆盖旧版本，而是调用 \lstinline|store.Put| 写入带有 Pending 标记的临时版本。该预写入过程为并发读操作提供了一个额外的判定条件：若并发读取请求的时间戳满足 $\lstinline|snapshotTime| \ge \lstinline|prepareTime|$，且遇到 Pending 标记，底层将返回 \lstinline|ErrPendingRead|，调用方随后进入等待或重试。待协调者最终作出提交决定后，\lstinline|Commit| 通过 \lstinline|store.ConfirmPending(txId, commitTime)| 将临时版本确认为正式版本。通过这一过程，预提交阶段与最终提交阶段之间的可见性得以衔接。

      \label{fig:quick-commit-implementation}
\end{figure}

在 \lstinline|QuickCommit| 的实现逻辑中，由于省略了 \lstinline|Prepare| 阶段，事务提交流程被压缩为一次单分片内的原子变更。引擎首先通过 \lstinline|clock.Tick()| 获取提交时间；随后，CAS 校验模块针对 PSI、SI 以及 SER 隔离级别执行乐观并发验证，以确认缓冲区中记录的 \lstinline|OriginalVersion| 仍为当前最新版本，避免覆盖写入。在通过版本校验并获取必要的本地写锁后，\lstinline|QuickCommit| 不再经过 Pending 预写入流程，而是将缓冲区中的数据直接以带有完整 \lstinline|commitTime| 的正式版本写入 MVCC 存储层。这样一来，校验、写入、提交与释放锁都在单一分片内完成，从而减少了单分片事务的提交路径。

\subsection{混合逻辑时钟}
在并发定序和版本可见性判断中，混合逻辑时钟（HLC）提供了统一的时间基准。本原型的 HLC 组件参考了开源项目 \lstinline|glycerine/hlc| 的实现思路，并用 Go 语言实现了一个并发安全的时钟模块。

在具体的运行层面，该时钟模块重点实现了两个用于时钟状态机推进的基石接口：
\begin{itemize}
      \item \textbf{本地时间获取（Now/Tick）}：当节点（路由或分片）内部产生本地事件，如分配事务快照时间或构建局部预备时间时，系统会调用该接口。算法读取当前主机的物理时间，并与本地维护的历史最高 HLC 时间进行比较。如果物理时钟前进，则推进 \lstinline|WallTime| 并将 \lstinline|Logical| 清零；如果检测到时钟停滞或物理时钟回退，则保持当前物理时间上界不变，并通过原子操作递增逻辑计数器，从而生成单调递增的时间戳。
      \item \textbf{远程时钟同步（Update/Receive）}：在跨节点请求中，底层 RPC 拦截器会在报文头部（Header）附带发送方当前的 HLC 时间戳。接收端在解析应用层载荷之前，先调用时钟同步逻辑，对“本地维护的当前 HLC”“报文携带的远程 HLC”以及“本机当前物理时间”三者进行比较，并据此更新本地时间状态。该过程用于在节点交互过程中维持时间顺序的一致性。
\end{itemize}

基于上述时钟组件及其在 RPC 通信过程中的配合，系统能够在分布式节点之间维持一致的时间比较基础。相比集中式发号方式，这种去中心化时钟机制避免了额外的中心协调开销，也为基于 MVCC 的快照读取以及 SER 级别下的冲突检测提供了统一的时间边界。

\subsection{通信原理与同步机制}

在分布式数据库系统中，协调者（Router）与各个分片（Shard）之间存在高频内部通信。考虑到事务执行路径对网络开销较为敏感，系统没有采用传统的 HTTP RESTful 方式，而是使用基于 \lstinline|Protobuf|（如 \lstinline|shardpb| 包所示）的 RPC 框架作为跨节点通信基础。

采用基于 \lstinline|Protobuf| 的 RPC 协议，主要是出于通信效率方面的考虑。一方面，\lstinline|Protobuf| 使用紧凑的二进制编码格式，相比 JSON 等文本协议可减少请求负载；另一方面，底层 RPC 框架依托 HTTP/2 的多路复用（Multiplexing）机制，使多个并发事务请求能够共享同一条底层 TCP 连接，从而降低连接建立与传输过程中的额外开销。

在事务处理的数据面之外，集群控制面中全局路由表、分片拓扑状态以及隔离级别元数据的同步同样至关重要。为了使分片节点能够以极低延迟感知集群状态变更，系统在配置同步链路中抛弃了传统的客户端定时轮询（Polling）模型，转而引入了基于流式 RPC（Streaming RPC）的长连接实时主动推送机制，图~\ref{fig:config-sync}展示了其时序图。

\begin{figure}[htbp]
      \centering
      \includegraphics[width=0.82\textwidth]{figures/mmd/long-conn.pdf}
      \caption{长连接配置同步示意图}
      \label{fig:config-sync}
\end{figure}

长连接配置同步策略主要带来两方面作用。其一，当全局元数据发生变更时，Router 可以通过常驻的数据流通道主动下发增量或全量配置，从而减少轮询机制带来的同步延迟和无效探测开销。其二，该长连接通道同时承担心跳保活（KeepAlive）功能，节点间的 Ping-Pong 心跳有助于 Router 较快感知底层分片的宕机或网络异常，并据此执行路由重定向与故障摘除（Failover）。

\subsection{用户客户端和测试客户端}

用户客户端的职责相对直接。客户端连接到路由节点（Router）后，用户可以通过命令行输入数据操作与事务管理命令。这里最关键的设计点不是交互形式，而是事务亲和性：同一事务的全部操作必须落到同一个 Router，才能保证事务上下文完整。基于这一要求，客户端只在事务开始时选择一次 Router；在该事务结束之前，后续读写、提交和中止请求都沿用这条连接。事务结束后，客户端再为下一笔事务重新选择路由节点。图~\ref{fig:user-client} 给出了原型系统命令行客户端的运行界面示例。

\begin{figure}[htbp]
      \centering
      \includegraphics[width=0.9\textwidth]{figures/code/user_client.pdf}
      \caption{原型系统 CLI 运行界面示例}

\end{figure}

图~\ref{fig:user-client} 展示了一个基于命令行交互的原型系统客户端运行截图。用户可以通过输入简单的命令来执行数据操作和事务管理，如开启事务、读写数据、提交或中止事务等。客户端会将用户输入的命令解析为相应的 RPC 请求，并发送到路由节点（Router）进行处理。
开启事务后，客户端会提示事务的ID，用户可以在事务上下文中继续执行读写操作，直到提交或中止事务。客户端还会显示操作的结果，如读取到的数据、写入是否成功、提交是否成功等。

在测试客户端（Test Client）方面，同一个事务的开启（Start）和后续操作（如 Read/Write）极有可能被路由到不同的路由节点（Router）。由于 Router 将事务上下文（活跃事务记录）维护在自身的进程内存中，这会导致后续节点因找不到事务上下文而抛出错误，破坏事务正确性。为解决该问题并满足高并发评测需求，测试客户端设计了基于 ClientPool 的连接与会话路由机制，其核心理念是将负载均衡的粒度从“每次 RPC”提升到了“每个事务”。该机制具备以下三个关键特性：

\begin{enumerate}
      \item \textbf{事务亲和性（Transaction Affinity）}：客户端在发起 Start 请求前，从池中为其分配一个固定的 Client 实例。该事务内的全部后续操作以及最终的 Commit 或 Abort，均强制通过该 Client 收发，确保了一笔事务的所有 RPC 能够一致且完整地打到同一个 Router 上。事务终结后绑定关系解除。
      \item \textbf{事务级负载均衡}：ClientPool 的分配调度利用原子计数器实现轮询逻辑，使高并发创建请求能够较均匀地分配到后端 Router。例如在 3 个 Router 和 10 个测试事务的场景下，各节点的承载比例大致为 4:3:3，从而减少明显的请求倾斜。
      \item \textbf{并发安全且无排他锁}：底层复用的 gRPC \lstinline|ClientConn| 本身支持并发安全与多路复用。因此，不同事务可以并发使用池中的同一个 Client，而不必采用“借出-上锁-归还”的排他模型。这样可以避免客户端池大小直接成为测试并发度的主要限制。
\end{enumerate}

\end{figure}

\subsection{系统日志与操作可观测性}

分布式数据库的性能调优与架构论证高度依赖于底层运行状态的透明化。本系统在分片（Shard）组件中内置了结构化的操作日志流（\lstinline|OpLog| 与 \lstinline|NoOpLog| 的灵活切换），并在事务执行的核心路径上无侵入地埋点了多维度的时间戳与状态指标。以此为基础，系统通过暴露核心指标构建了完整的可观测性监控体系，旨在以详实的实测数据支撑并验证系统在并发调度上的架构优势。

本项目的一个核心论证目标在于“探究混合隔离级别相比单一隔离级别在执行性能上的优势”。为了使这一命题可被量化，可观测性层面进行了针对性的精细粒度设计：
系统中每一阶段的生命周期事件（包括跨分片的 \lstinline|Prepare| 和 \lstinline|Commit|，以及单分片优化的 \lstinline|QuickCommit|）均会显式记录其绑定的隔离级别（\lstinline|IsolationLevel|）元数据以及对应的操作耗时（RRT, Round-Trip Time）。不仅如此，系统还通过 \lstinline|LockManager| 精确记录了高并发场景下悲观锁（尤其是 SER 隔离级别引发的共享读锁与排他写锁）排队阶段的跨事务真实锁等待耗时（Lock Wait Time）；同时在乐观并发控制（如 SI 级别）通过版本比对的 CAS 执行域内，也对因写写冲突导致回滚（Abort Rate）和触发由于遇到 Pending 标志而被异常拦截的读取（\lstinline|ErrPendingRead| 拦截率）进行了频率统计。

通过对上述多源探针数据的采集、聚合与可视化，系统能够较细致地呈现不同并发负载下的执行过程。这些监控数据表明，在混合隔离负载下，将核心事务保持为 SER，而将后台批处理或只读分析事务放宽至 SI 或 PC 后，系统可以利用 MVCC 的历史版本读取机制减少部分由强隔离带来的锁争用与排队开销。结合基准测试结果可以看出，混合隔离配置在当前原型系统中与更高吞吐量和较低排队开销相对应。

\section{本章小结}

本章说明了原型系统的定位、需求边界以及关键实现。系统采用分布式架构，支持 PC、PSI、SI 和 SER 四种隔离级别混合运行，并围绕全内存 MVCC 存储、基于 HLC 的时间定序、跨分片事务协调和客户端路由机制给出了具体实现。该原型为下一章的系统测试提供了可运行的实验平台。
