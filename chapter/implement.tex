\chapter{分布式KV数据库原型的架构设计与实现}
本章的将基于前序章节中关于分布式数据库的建模和分析，以及经\TLAPlus 验证过的支持混合隔离级别的分布式数据库操作语义，设计并实现一个数据库原型系统，用于验证该操作语义相较于只支持单一隔离级别的操作语义在性能上的优势。

\section{需求分析}
本文中的数据库原型系统旨在实现一个分布式数据库原型，用于验证支持混合隔离级别的操作语义相较于单一隔离级别操作语义在性能上的优势。为了满足这一目标，需要对设计目标进行需求分析，明确系统的功能需求和非功能需求。

\subsection{功能需求}
功能需求定义了系统必须完成的具体任务和行为。基于验证混合隔离级别性能优势的目标，系统的主要功能需求如下：

\begin{enumerate}
    \item \textbf{基本数据操作}：本原型系统作为一个键值（Key-Value）数据库，需支持基本的读（Get）、写（Put）、增（Insert）、删（Delete）四种数据操作。数据模型以键值对（Key-Value）形式存储，不支持复杂的嵌套文档结构。
    \item \textbf{分布式集群管理}：
          \begin{itemize}
              \item \textbf{分片（Sharding）}：支持将数据水平切分并分布在多个分片节点上。
              \item \textbf{路由（Routing）}：客户端通过路由节点访问数据，路由节点根据分片键将请求转发至正确的分片。
          \end{itemize}
    \item \textbf{事务管理}：
          \begin{itemize}
              \item \textbf{事务生命周期}：支持事务的开启（Start）、提交（Commit）和中止（Abort）。
              \item \textbf{跨分片事务}：支持涉及多个分片的分布式事务，保证原子性。
          \end{itemize}
    \item \textbf{混合隔离级别支持}：这是本系统的核心需求。系统允许客户端在开启事务时指定该事务的隔离级别。系统应至少支持以下几种隔离级别的混合运行：
          \begin{itemize}
              \item \textbf{前缀一致性（Prefix Consistency, PC）}
              \item \textbf{并行快照隔离（Parallel Snapshot Isolation, PSI）}
              \item \textbf{快照隔离（Snapshot Isolation, SI）}
              \item \textbf{可串行化（Serializable, SER）}
          \end{itemize}
          系统需要确保在上述隔离级别混合运行时，不仅能保证各自隔离级别的语义，还能保证数据的一致性和正确性。
\end{enumerate}

\subsection{非功能需求}
非功能需求涉及系统的性能、可靠性等方面：
\begin{enumerate}
    \item \textbf{高性能}：由于采用了全内存存储，系统应具有较低的读写延迟和较高的吞吐量。
    \item \textbf{可扩展性}：系统应支持水平扩展，通过增加分片节点来线性提升存储和处理能力。
    \item \textbf{可观测性}：为了验证性能优势，系统必须提供详细的性能监控指标（如延迟、吞吐量、冲突率等），以便进行后续的实验对比。
\end{enumerate}

\subsection{用例分析}
系统主要涉及两类角色：客户端用户（Client）和系统管理员（Admin）。
\begin{itemize}
    \item \textbf{客户端用户}：主要进行数据的读写操作和事务处理。他们可以发起普通读写请求，也可以开启特定隔离级别的事务进行一系列操作。
    \item \textbf{系统管理员}：负责集群的配置，如添加分片、配置路由规则等。
\end{itemize}

\section{系统设计}
基于上述需求分析，本节将对数据库原型系统进行总体架构设计和模块设计。

\subsection{总体架构设计}
本系统采用经典的 Shared-nothing 分布式架构，参考 MongoDB 的集群模型，主要由三类组件构成：路由节点（Router）、配置节点（Config Server）和分片节点（Shard Server）。
整体组件关系如图~\ref{fig:architecture} 所示。

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.9\textwidth]{figures/mmd/architecture.pdf}
    \caption{系统总体架构图}
    \label{fig:architecture}
\end{figure}

各组件职责如下：
\begin{itemize}
    \item \textbf{路由节点（Router）}：
          作为集群的统一入口，对外提供以 MySQL 或自定义协议的接口。
          路由节点不存储实际数据，只缓存元数据（Metadata）。
          它负责解析客户端请求，根据分片键（Shard Key）和路由表（Routing Table）将请求路由到具体的分片节点。
          对于跨分片事务，路由节点充当事务协调者（Coordinator）的角色，负责两阶段提交（2PC）的协调工作。

    \item \textbf{配置节点（Config Server）}：
          存储集群的元数据，包括分片信息、路由表规则、节点状态等。
          保证元数据的高可用和强一致性是配置节点的关键，但在本原型中，为了简化实现，可采用单点或简单的副本机制。

    \item \textbf{分片节点（Shard Server）}：
          负责实际数据的存储和操作执行。
          每个分片节点维护一部分数据，并包含本地的事务执行引擎和存储引擎。
          分片节点作为分布式事务的参与者（Participant），响应协调者的指令，并负责本地数据的并发控制（Concurrency Control）。
\end{itemize}

\subsection{核心模块设计}

\subsubsection{存储引擎设计}
为了简化实现并聚焦于并发控制机制的验证，本原型采用全内存存储引擎。数据在内存中以 Key-Value 的形式组织，了支持多版本并发控制（MVCC），每个 Key 对应的值不仅仅是一个单一数据，而是一个版本链（Version Chain）。
\begin{itemize}
    \item \textbf{多版本数据结构}：每个数据项包含多个版本，每个版本携带创建该版本的事务时间戳（Commit Timestamp）和实际数据载荷。
    \item \textbf{内存索引}：使用哈希表（Hash Map）或 跳表（Skip List）作为索引结构，实现 $O(1)$ 或 $O(\log N)$ 的快速查找。
\end{itemize}

\subsubsection{事务管理模块设计}
事务管理模块是系统的核心，分为协调者模块（位于 Router）和参与者模块（位于 Shard）。

\begin{enumerate}
    \item \textbf{混合逻辑时钟（HLC）}：
          系统采用 HLC 作为时间源。HLC 提供了单调递增的时间戳，用于定序事务和版本控制。

    \item \textbf{并发控制协议}：
          为了支持混合隔离级别，系统采用基于时间戳的 MVCC 协议。
          \begin{itemize}
              \item 对于 \textbf{Prefix Consistency (PC)} 事务，读取全局仲裁序列某个一致前缀上的可见版本，避免观察到带“空洞”的历史。
              \item 对于 \textbf{Parallel Snapshot Isolation (PSI)} 事务，允许在不同的分片上读取到不同快照的数据，但在同一分片上满足 SI。
              \item 对于 \textbf{Snapshot Isolation (SI)} 事务，在事务开始时获取快照时间戳（StartTS），读取 CommitTS $\le$ StartTS 的最新版本。
              \item 对于 \textbf{Serializable (SER)} 事务，除了遵循 SI 的读规则外，还需进行冲突检测（如写偏斜检测），确保可串行化。
          \end{itemize}

    \item \textbf{分布式事务原子性}：
          采用两阶段提交（2PC）协议。
          \begin{itemize}
              \item \textbf{Prepare 阶段}：协调者向所有参与者发送 Prepare 请求，参与者执行本地事务逻辑，锁定资源，并持久化（在内存中模拟）事务意向。
              \item \textbf{Commit/Abort 阶段}：如果所有参与者 Prepare 成功，协调者发送 Commit，否则发送 Abort。
          \end{itemize}
\end{enumerate}

\subsubsection{通信模块设计}
节点间通信采用异步 I/O 模型（如 RPC 或 TCP 长连接），以减少网络通信开销。消息定义采用 Protobuf 等序列化格式，确保高效传输。

\section{实现}
\subsection{基于高性能RPC的底层通信与长连接配置同步机制}

在分布式数据库系统中，协调者（Router）与底层的各个存储分片（Shard）之间存在着高频且密集的内部通信。为了打破网络I/O带来的延迟瓶颈，系统底层摒弃了传统的 HTTP RESTful 架构，全面采用了基于 \lstinline|Protobuf|（如 \lstinline|shardpb| 包所示）的高性能 RPC 框架作为跨节点的通信基座。

使用高性能 RPC 协议具有诸多显著的架构优势：首先，\lstinline|Protobuf| 采用紧凑的二进制编码格式，其序列化与反序列化速率远超 JSON 等文本协议，极大压缩了事务在预备（Prepare）、提交（Commit）以及快速提交（QuickCommit）链路中的请求负载；其次，底层的 RPC 框架依托 HTTP/2 协议的多路复用（Multiplexing）机制，允许海量并发事务的 RPC 请求共享同一条底层 TCP 物理链路，彻底消除了频繁三次握手带来的网络开销，并有效规避了队头阻塞（Head-of-Line Blocking）问题。

在事务处理的数据面之外，集群控制面中全局路由表、分片拓扑状态以及隔离级别元数据的同步同样至关重要。为了使分片节点能够以极低延迟感知集群状态变更，系统在配置同步链路中抛弃了传统的客户端定时轮询（Polling）模型，转而引入了基于流式 RPC（Streaming RPC）的长连接实时主动推送机制，图~\ref{fig:config-sync}展示了其时序图。

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.82\textwidth]{figures/mmd/long-conn.pdf}
    \caption{长连接配置同步示意图}
    \label{fig:config-sync}
\end{figure}

长连接配置同步策略具备极为突出的优势：其一，实现了配置状态的“毫秒级”触达。当全局元数据发生变更时，Router 可以利用常驻的下行数据流通路，主动将增量或全量配置即时下推至各个 Shard 节点，彻底杜绝了轮询机制带来的时间窗口延迟以及无变更时的无效探测网络损耗。其二，该长连接通道天然兼具心跳保活（KeepAlive）的探针功能。在实时下发配置的同时，节点间的 Ping-Pong 心跳使得 Router 能够极度灵敏地捕捉到某个底层分片的宕机或网络割裂异常，进而快速在协调者端触发路由重定向与故障摘除（Failover），从架构底层夯实了分布式事务系统运行的极高可用性与状态一致性。



\subsection{存储分片与分布式事务的核心代码实现}

在分布式数据库架构中，数据分片（Shard）组件不仅承担着数据实例的物理存储与多版本管理责任，同时也是执行全局或局部事务、保障隔离级别的核心流转节点。系统内部通过 \lstinline|shard| 包下的 \lstinline|Shard| 结构体实现了对底层状态机的封装。本小节将从高维角度对分片内多版本读写引擎、事务状态管理、两阶段提交（2PC）的可见性缺陷修复以及单分片优化机制的实现细节展开深入论述。

本文的代码提供在仓库 \url{https://github.com/ZhangJihua0327/let-mil-go}中。

\subsubsection{事务操作信息的分层与局部化管理}
本系统采用了“全局协调计算，局部状态下推”的事务信息管理范式。在事务生命周期初始化阶段（\lstinline|TxStart|），事务的全局元数据（如事务ID、隔离级别和全局快照时间戳 \lstinline|snapshotTime|）由协调者（Router）统一获取并下发。这种设计能够让不同分片共享同一个全局时间基准，进而支持前缀一致性（PC）、快照隔离（SI）以及严格可串行化（SER）。图~\ref{fig:global-timeline} 展示了全局事务信息的分发与下推流程，协调者在事务开始时通过 RPC 将全局元数据广播至所有相关分片，确保每个参与者节点都能基于同一时间线进行版本控制和并发调度。


\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.9\textwidth]{figures/mmd/global-timeline.pdf}
    \caption{组件交互时序图}
    \label{fig:global-timeline}
\end{figure}

相对地，涉及具体分片的数据操作信息则通过分片内的 \lstinline|TxBufferManager| 进行局部维护。由于未决事务的读写集极可能导致极大的内存开销，代码在此处采用了懒加载（Lazy Load）机制：只有当该分片真正执行首次 \lstinline|TxRead| 或 \lstinline|TxWrite| 时，才会实例化对应事务的局部缓存（\lstinline|TxBuffer|）。这种分阶段存储策略大幅降低了分布式协同节点的通信负担，保证了内存状态的局部聚焦性。

\subsubsection{基于MVCC引擎的多版本读写流转}
分片底层的无锁化读并发依赖于多版本并发控制（MVCC）模型。以 \lstinline|TxRead| 为例，代码在读取数据时，严格遵循“读己之所写（Read-Your-Own-Writes）”的内部一致性：系统首先探测本地事务缓冲区的 Write 集合，命中后判断记录是否带有删除标记（Deleted）。如果本地无修改记录，读请求将穿透至底层的 \lstinline|MVCCStore| 操作对象，基于给定的 \lstinline|snapshotTime| 定位并获取小于但最接近该时钟的可用历史版本。

此外，程序还为最高隔离级别（SER）引入了悲观的锁机制转换。如果事务的隔离级别为 SER，分片内部将直接通过 \lstinline|lockMgr.AcquireRead| 强制索取分布式共享锁，在读写阶段即时屏蔽幻读和写倾斜缺陷，从而保证全局事务的严格串行化调度。

\subsubsection{两阶段提交可见性漏洞(Hole)的消除}
在标准的分布式两阶段提交（2PC）协议中，由于多个参与者节点的 \lstinline|Prepare| 阶段无法做到绝对原子同频，常存在所谓的可见性漏洞（Visibility Hole）——即事务虽然已经预定将要提交，但若并发的读取操作携带了更大（或相同）的时间戳进入，可能会因为读取到旧版本而破坏线性一致性。

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.9\textwidth]{figures/mmd/2pc-hole.pdf}
    \caption{两阶段提交可见性漏洞示意图}
    \label{fig:2pc-hole}
\end{figure}

图~\ref{fig:2pc-hole}展示了本组件如何解决两阶段提交可见性漏洞的解决方式。本组件借助未决状态（Pending Status）与时间戳推进解决了该漏洞：系统在 \lstinline|Prepare| 阶段，根据混合逻辑时钟（HLC）派生出本地的预备时间 \lstinline|prepareTime|。此时并未直接覆盖老数据，而是调用 \lstinline|store.Put| 打上 Pending 标记以及临时版本号。这一预写行为充当了并发读操作的前向屏障：倘若并发读查询的时间戳满足 $\lstinline|snapshotTime| \ge \lstinline|prepareTime|$ 并且遇到了 Pending 标位，底层将抛出 \lstinline|ErrPendingRead|。这一拦截行为促使过早发起读取操作的调用方陷入阻塞或执行安全重试。直至最终协调者下达任务并在 \lstinline|Commit| 函数内通过 \lstinline|store.ConfirmPending(txId, commitTime)| 将版本信息实化确立，系统的时钟推进即可闭环，可见性漏洞得以彻底消除。

\subsubsection{单分片快速提交(QuickCommit)优化}
当系统规划器判定当前事务的作用域仅局限于某单一分片时，该组件会触发 \lstinline|QuickCommit| 的快速提交路径，以规避2PC的网络协商与多次RPC的延迟开销\cite{fastcommit,fastcommit2}，如图~\ref{fig:quick-commit-implementation}。
\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.85\textwidth]{figures/mmd/quick-commit.pdf}
    \caption{组件交互时序图}

在 \lstinline|QuickCommit| 的实现逻辑中，由于剔除了 \lstinline|Prepare| 阶段，事务的操作直接收敛为单次原子变更：引擎首先基于 \lstinline|clock.Tick()| 获取即时的决议时间；随后的 CAS 校验模块针对 PSI/SI 以及 SER 隔离级别执行乐观并发验证，确保持有缓冲区数据的 \lstinline|OriginalVersion| 仍然是当前系统中的最新版本以防覆盖写入。在通过版本校验且获取必要的本地写锁之后，\lstinline|QuickCommit| 将直接跳过 Pending 预写入流程，把缓冲池内的数据带有完整的 \lstinline|commitTime| 非挂起标志（将 pending 设为 \lstinline|false|，原版本置为 \lstinline|0|）径直向 MVCC 底层固化。由于校验、写入、提交与释放锁在单一分片层级形成了一个闭环，在保障 ACID 语义不被破坏的前提下，极大提升了单分片事务的并发吞吐能力。

\subsection{混合逻辑时钟}
在分布式事务的并发定序与多版本可见性判断中，混合逻辑时钟（HLC）扮演着时间基准的核心角色。本原型的 HLC 组件在底层实现上参考了开源社区成熟的 \lstinline|glycerine/hlc| 算法模型，通过 Go 语言构建了一个高性能、并发安全的全局时钟模块。

在具体的运行层面，该时钟模块重点实现了两个用于时钟状态机推进的基石接口：
\begin{itemize}
    \item \textbf{本地时间获取（Now/Tick）}：当节点（路由或分片）内部独立产生分布事件（如分配事务快照时间、构建局部预备时间等）时发起调用。算法实时获取当前主机的设备物理时间，并与本地内存中维护的历史最高 HLC 时间进行比对。如果主机时钟前进（大于记录的最高物理时间），则相应推进 \lstinline|WallTime| 并将 \lstinline|Logical| 清零；倘若检测到时钟停滞乃至发生物理时钟倒退，此时物理发生时间维持为本地已有最大值不变，转而通过原子操作（Atomic）递增逻辑计数器，由此生成单调递增的合法衍生时间戳以保障内部事件的时间定序。
    \item \textbf{远程时钟同步（Update/Receive）}：依托前文所述的高性能 RPC 框架系统，集群内任何跨节点的交互请求（包括路由于开启事务时向分片下发全局元数据、分片间协同调度数据等）都会利用底层 RPC 拦截器在报文头部（Header）自动植入请求方的当前 HLC 时间戳。当流经的目标节点（接收端）在解析应用层载荷之前，中间件会被触达并优先调用时钟同步逻辑。内部算法会同时比较“本地维护的当前 HLC”、“接收报文携带的远程 HLC”以及“本机设备此刻的真实物理时间”，取三者中的最高边界值并安全合并为本地计算域中最新的时间状态。
\end{itemize}

基于这一高度解耦的时钟机制组件并在底层 RPC 通信切面上的无缝穿插，分布式节点的因果定序在系统网络交互的每一个端点被同步推演。这种实现以去中心化的时钟推挽方式规避了集中发号器的请求瓶颈，同样也为基于 MVCC 引擎实施快照读（如支持 SI、PSI 隔离级别的隔离域查询）和严格冲突检测（如可串行化 SER 级别的跨维度校验）构建了确切而一致的时钟边界和比较屏障。

\subsection{用户客户端和测试客户端的实现}

用户客户端的实现相对简单，客户端连接到路由节点（Router）后，用户可以通过命令行交互的方式输入各种数据操作和事务管理命令，并且通过负载均衡策略选择合适的路由节点进行请求。在实现客户端的过程中，主要关注事务的亲和度，也就是确保同一事务的所有操作都能够路由到同一个路由节点（Router）上，以保证事务上下文的一致性和正确性。在当前逻辑下，只有当开启新事务时，才会通过负载均衡策略选择一个路由节点（Router）进行连接，并且在该事务的整个生命周期内，所有的操作都将通过该连接发送到同一个路由节点（Router）。当事务结束后，客户端会断开与该路由节点（Router）的连接，并且在下一次开启新事务时再次通过负载均衡策略选择一个路由节点（Router）进行连接。

图~\ref{fig:user-client} 展示了一个基于命令行交互的用户客户端示例。用户可以通过输入简单的命令来执行数据操作和事务管理，如开启事务、读写数据、提交或中止事务等。客户端会将用户输入的命令解析为相应的 RPC 请求，并发送到路由节点（Router）进行处理。
开启事务后，客户端会提示事务的ID，用户可以在事务上下文中继续执行读写操作，直到提交或中止事务。客户端还会显示操作的结果，如读取到的数据、写入是否成功、提交是否成功等。

在测试客户端（Test Client）方面，同一个事务的开启（Start）和后续操作（如 Read/Write）极有可能被路由到不同的路由节点（Router）。由于 Router 将事务上下文（活跃事务记录）维护在自身的进程内存中，这会导致后续节点因找不到事务上下文而抛出错误，破坏事务正确性。为解决该问题并满足高并发评测需求，测试客户端设计了基于 ClientPool 的连接与会话路由机制，其核心理念是将负载均衡的粒度从“每次 RPC”提升到了“每个事务”。该机制具备以下三个关键特性：

\begin{enumerate}
    \item \textbf{事务亲和性（Transaction Affinity）}：客户端在发起 Start 请求前，从池中为其分配一个固定的 Client 实例。该事务内的全部后续操作以及最终的 Commit 或 Abort，均强制通过该 Client 收发，确保了一笔事务的所有 RPC 能够一致且完整地打到同一个 Router 上。事务终结后绑定关系解除。
    \item \textbf{事务级负载均衡}：ClientPool 的分配调度利用原子计数器实现了轮询逻辑，以此保障在高并发创建请求打入时，能够将海量的新增事务均匀地打散分配给后端的各个 Router。例如面对 3 个 Router 和 10 个测试事务，各节点的承载比例能够稳定控制在大致 4:3:3，有效地避免了请求倾斜。
    \item \textbf{并发安全且无排他锁}：底层复用的 gRPC \lstinline|ClientConn| 具有原生并发安全的特性且支持多路复用。因此，不同事务可以同时并发持有和使用池中的同一个 Client（路由节点通过 txID 严格区分不同事务），而无需采用低效的“借出-上锁-归还”排他模型。这种非排他设计保证了测试机的并发上限不会被客户端池数量所限，进而可提供极高的测试吞吐。
\end{enumerate}

测试用例通过配置文件的方式输入，测试客户端读取测试用例后，按照用例中定义的事务操作序列和隔离级别要求，自动执行。附录~\ref{app:testcase} 中的图~\ref{fig:testcase} 展示了一个测试配置文件的示例。第一行的数字指定worker的数量，worker代表着每一个独立线程，随后定义每个worker要执行的事务的顺序和事务内部的操作细节。测试客户端会根据配置文件中的定义，自动创建相应数量的worker。每个worker会按照配置文件中定义的事务操作序列，依次执行事务的开启、读写操作以及提交或中止等步骤。在执行过程中，测试客户端会记录每个操作的结果和性能指标，以便后续分析和验证。


\subsection{系统日志与操作可观测性的多维实现}

分布式数据库的性能调优与架构论证高度依赖于底层运行状态的透明化。本系统在分片（Shard）组件中内置了结构化的操作日志流（\lstinline|OpLog| 与 \lstinline|NoOpLog| 的灵活切换），并在事务执行的核心路径上无侵入地埋点了多维度的时间戳与状态指标。以此为基础，系统通过暴露核心指标构建了完整的可观测性监控体系，旨在以详实的实测数据支撑并验证系统在并发调度上的架构优势。

本项目的一个核心论证目标在于“探究混合隔离级别相比单一隔离级别在执行性能上的优势”。为了使这一命题可被量化，可观测性层面进行了针对性的精细粒度设计：
系统中每一阶段的生命周期事件（包括跨分片的 \lstinline|Prepare| 和 \lstinline|Commit|，以及单分片优化的 \lstinline|QuickCommit|）均会显式记录其绑定的隔离级别（\lstinline|IsolationLevel|）元数据以及对应的操作耗时（RRT, Round-Trip Time）。不仅如此，系统还通过 \lstinline|LockManager| 精确记录了高并发场景下悲观锁（尤其是 SER 隔离级别引发的共享读锁与排他写锁）排队阶段的跨事务真实锁等待耗时（Lock Wait Time）；同时在乐观并发控制（如 SI 级别）通过版本比对的 CAS 执行域内，也对因写写冲突导致回滚（Abort Rate）和触发由于遇到 Pending 标志而被异常拦截的读取（\lstinline|ErrPendingRead| 拦截率）进行了频率统计。

通过对上述多源探针数据的采集与聚合并引入可视化监控大盘，系统能够精确重现各种并发负载下的微观执行轨迹。实测大盘直观地证实了论点：当业务流量引入混合隔离负载——即将金融级核心链路配置为严格可串行化（SER），而将后台批处理与只读分析放宽至快照隔离（SI）或前缀一致性（PC）时，依靠底层 MVCC 引擎非阻塞的快照历史版本读取机制，可以有效规避 SER 隔离级别因强制加锁而带来的锁争用与队伍积压。客观的基准测试监控数据切实验证了，混合隔离架构不仅以极细粒度地保障了核心业务的事务串行安全性，更凭借低级别隔离的并发读取打破了全库极严管治的“性能护城河”，显著缩小了读写排队开销，使得整体分布式集群系统吞吐率（TPS）和请求长尾延迟（P99 Latency）获得了实质性的优化与飞跃。

\section{本章小结}

本章详细阐述了用于验证混合隔离级别性能优势的分布式数据库原型系统的架构设计与实现。首先通过需求分析确立了系统功能，明确了对PC、PSI、SI和SER四种隔离级别混合运行的支持。确立了无共享架构并设计了全内存MVCC存储引擎与基于HLC的并发控制协议。随后深入剖析了RPC框架、无锁多版本请求流转、未决时钟机制消除可见性漏洞等底层关键技术的工程实现。本章所述原型系统的落地，为后续章节全面评测混合隔离级别在提升吞吐量与降低延迟方面的优势提供了坚实的实验基座。
